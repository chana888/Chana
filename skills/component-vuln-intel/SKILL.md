## 组件情报检索

识别产品不等于存在漏洞。先记录组件来源、版本可信度、真实入口及部署上下文，再按相关性选择情报渠道；不要求每次执行固定全套搜索。

- 优先查厂商公告、GitHub Advisories、CVE 记录和本地知识库；需确认触发条件时补充公开技术分析及 PoC 源码。
- 可用 `searchsploit <组件> <版本>`、搜索工具、HTTP 客户端或 GitHub API。读取页面、查库、分析依赖及 PoC 属于静态/情报工作，不调用 `mcp__chrome_mcp__*`。
- 中文分析可参考先知、Seebug、FreeBuf、奇安信等；仅在需要交叉核实时增加渠道，不按搜索引擎数量验收。
- 依赖只追踪与可达调用链或版本风险相关的条目，不对每个依赖递归执行全部查询。
- 资产引擎结果只作为归属线索，不因发现同组件实例自动扩大授权或向新资产发送验证请求。

## 产出与验证交接

每条情报记录来源 URL、检索日期、受影响版本、前置条件、触发入口、修复条件和与当前目标的匹配证据。情报结论以 `tentative` 跟踪；版本未知或入口未证实时保留缺口，不推断漏洞成立。

候选先登记 D1 假设、正常对照、预期信号、范围、预算与停止条件，再由 D2 定向验证。只有补充目标页面正常功能请求时才读取 `vps-browser-workflow` 并使用 `mcp__chrome_mcp__*`，同时确认 UI 变化及可归因的正常请求。不得因搜到 PoC 自动运行利用。

搜索受阻时在本轮预算内改用官方公告、API、本地库或另一可用渠道。记录实际查询条件及失败原因；没有结果或渠道受阻不能写成“全渠道无公开漏洞”，也不触发盲打。回到 D0 补发现或选择下一条 D1 假设。
